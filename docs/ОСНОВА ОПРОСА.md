## 2. Режимы адаптера и их обязанности

Опрос блоков работает в **режиме с заголовками** (`ATH1`), остальное приложение — по-прежнему в `ATH0`.
Переключение только внутри `scanModules`, в `finally` всё возвращается (`ATH0`, `ATAR`, `ATFCSM 0`, `ATCEA` выкл,
`ATST 64`, `ATAT1`, стандартный заголовок OBD).

Нужные команды и где появились (клон «v1.5» ≈ v1.4b): `ATCF`/`ATCM` (v1.0), `ATFCSH/SD/SM` (v1.1), `ATCRA hhh` (v1.3),
`ATCEA` (v1.4), `ATCP` (v1.0). `ATCRA` с `X` и 4-байтный `ATSH` — только v2.0, **не использовать**.

Проверка адаптера (уже есть, `probeAdapter`): недостающие команды → в `AdapterInfo.missing`. Для универсального поиска
критичны `ATCF`/`ATCM`; без них — запасной путь «фильтр по паре» (п. 4.4).

## 3. Формат строк при `ATH1 ATCAF1 ATS1` (парсер `Frames`)

Каждый CAN-кадр — отдельная строка: **ID, затем байты данных вместе с PCI** (ELM в H1 не склеивает кадры и не печатает
`0:`/`1:` и строку длины — это только для H0).

```
7E8 06 41 00 BE 3F B8 13          одиночный кадр: PCI 0x06 = 6 байт данных
77E 10 13 59 02 FF 13 05 08       первый кадр: PCI 0x10, длина 0x013 = 19
77E 21 2C 21 39 01 2C 11 80       продолжение №1
77E 22 02 2C 21 35 01 2C AA       продолжение №2 (хвост — заполнитель, обрезаем по длине)
18 DA F1 10 06 41 00 BE 3F B8 13  29 бит: 4 байта ID
```

Правила парсера:
1. Строка → `(id, bytes)`. 11 бит: первое поле из 3 hex-символов; 29 бит: четыре пары hex в начале (признак — протокол 7/9).
   При `ATS0` (если `ATS1` не принялся): первые 3 (или 8) символов — ID, дальше пары.
2. Сборка ISO-TP **по ID**: `0L` — одиночный кадр (L байт); `1LLL` — первый кадр (длина 12 бит), `2N` — продолжения по порядку.
   Сообщение закрыто, когда набрана заявленная длина; лишние байты (заполнители `AA/55/FF/00`) отбрасываются.
   Неполное сообщение (пришёл только первый кадр) возвращается с флагом `partial = true` — это сигнал «нужен ручной
   поток и повтор», а не мусор.
3. При расширенной адресации (`ATCEA`) первый байт данных — адрес; ELM его **не снимает в H1**: парсер получает флаг
   `extAddr` и сдвигает PCI на байт (одиночный кадр несёт ≤ 6 байт).
4. Служебные строки (`SEARCHING...`, `NO DATA`, `CAN ERROR`, `BUFFER FULL`, `STOPPED`, `?`) — в `status`, не в данные.
5. Результат: `List<Frame(id, data, partial)>` → `messages()` для существующих разборов `ModuleDecoder`.

Старый `ObdDecoder.messages` (формат H0) остаётся для OBD-части.

## 4. Поиск блоков (универсальный, без марки)

### 4.1 Подготовка
```
ATH1  ATCAF1  ATCFC1  ATAT0  ATST 32   ; 200 мс на ответ; ATS1 уже стоит
11 бит: ATCF 700  ATCM 700             ; принимать всё 0x700–0x7FF
29 бит: ATCP 18 ; ATCF 18DAF100  ATCM 1FFFFF00   ; принимать 18DAF1xx (ответ любому блоку тестеру F1)
```
Если `ATCF`/`ATCM` ответили `?` → п. 4.4.

### 4.2 Зонд — сразу настоящий запрос памяти ошибок
На каждый адрес шлём **`19 02 FF`**, а не «тестер-презент». Любой ответ с любого ID выдаёт блок и его ID ответа:
- одиночный кадр `59 02 …` — память пуста или 1 код, читать больше нечего;
- первый кадр `10 LL 59 02 …` — блок найден; если пара стандартная (+8), автопоток ELM уже всё собрал;
  иначе `partial` → после сверки пары повторяем с ручным потоком (п. 5);
- `7F 19 11/12/7F` — блок есть, UDS не понимает → KWP (п. 5);
- `7F 19 78` — «подожди»: ждём 1 с, `ATST FF`, повтор;
- `7F 19 22/7E` — нужна сессия: `10 03`, повтор;
- ничего — адреса нет.

Так один проход даёт и список блоков, и коды у большинства из них.

### 4.3 Порядок адресов (11 бит)
Полный диапазон `0x700–0x7FF` минус запрещённое: **`0x7DF`** (широковещательный) и диапазон ответов `0x7E8–0x7EF`.
Сначала «горячие» адреса, чтобы прогресс был виден сразу: `7E0–7E7`, затем `7D0–7DF`, `7A0–7CF`, `700–79F`.
Перед физическим перебором — один широковещательный `7DF: 19 02 FF`… **нет**: функциональный запрос заставит все
блоки отвечать одновременно многокадрово, ELM захлебнётся (`BUFFER FULL`). Только физические адреса.

Адреса ниже 0x700 (GM 0x24x → 0x64x, PSA 0x6xx) — второй проход, только если VIN говорит GM/PSA/Mercedes
(марочный профиль, шаг 3) или если за первый проход не нашлось ничего кроме двигателя.

Стоимость: ~224 адреса × (ATSH + запрос ≈ 2 команды × ~60 мс + 200 мс ожидания) ≈ 70–80 с по Bluetooth.
Прогресс показывается по адресам; «найдено N» — по мере находок.

### 4.4 Без `ATCF`/`ATCM` (урезанный клон)
Перебор с `ATCRA` по **каждому кандидату смещения**: +8, +0x6A, +0x20, −0x20, +1 — пять запросов на адрес слишком
дорого; поэтому для таких адаптеров: +8 для всех адресов, остальные смещения — только из марочного профиля.
В журнале честно: «адаптер не умеет фильтр диапазона, часть блоков может быть не найдена».

### 4.5 Сверка пары запрос/ответ
Ответ на запрос к `0x7xx` пришёл с `0xRRR`. Запоминаем пару. Если за один запрос ответили **несколько** ID
(бывает на шлюзах) — каждому своя запись, но помечаем «ответ на общий запрос» и повторяем запрос с фильтром
`ATCRA RRR`, чтобы подтвердить.

### 4.6 29-битная шина
Тот же зонд по `ATSH DA xx F1` для `xx = 00..FF` (кроме `F1` и `33`), сначала известные: `10 18 28 30 53 60 61 B0 B5 EF 0E 0B 1E 2B 00–7F`,
затем остальное. Ответ `18 DA F1 xx`. Автопоток ELM здесь работает (он меняет местами TA/SA), ручной — `ATFCSH DAxxF1`.

### 4.7 Расширенная адресация (шлюзы)
Отдельные профили поверх того же парсера и того же чтения: **BMW** `ATSH 6F1` + `ATCEA xx` + `ATCRA 6xx` (уже есть,
переводится на `Frames`), **Toyota** `ATSH 750` + `ATCEA xx` + ответ `758` (шаг 3). Запускаются по марке из VIN,
а при неизвестной марке — если обычный перебор нашёл ≤ 2 блоков и адаптер умеет `ATCEA`: пробуем 6F1 (три адреса
12/40/60) и 750 (три подадреса 40/5F/0F) — по шесть запросов, дёшево.

## 5. Чтение памяти ошибок из найденного блока

```
ATSH <req>   ATCRA <resp>   ATFCSH <req>   ATFCSD 30 00 14   ATFCSM 1   ATST 64
```
(для 29 бит `ATCP 18`, `ATSH DAxxF1`, `ATCRA 18DAF1xx`, `ATFCSH DAxxF1`; для CEA — `ATFCSD <xx> 30 00 14`.)

Третий байт нашего кадра управления потоком — пауза между кадрами STmin = 20 мс, не 0. С нулём блок сыплет продолжения
через ~1 мс, а клон переливает их в Bluetooth (38400 бод) медленнее, чем принимает: на Audi A4 B8 (лог 17.10.2026)
двигатель отдал 65 записей = 263 байта = 38 кадров, буфер ELM327 v1.5 переполнился на 12-м кадре (`BUFFER FULL`),
и ответ пропал целиком. 20 мс × 38 кадров = 0,8 с — терпимо, адаптер успевает и на 29-битных заголовках.

Порядок диалектов, останавливаемся на первом разобранном ответе:
1. UDS `19 02 FF` → `59 02 <маска> [DTC3 + статус]×n` (разбор уже есть: `parseUdsDetailed`, BMW — 6 hex).
2. `7F 19 78` → ждать до 5 с и повторить. `7F 19 22/7E` → `10 03`, повтор один раз.
3. Ответ всё равно обрезан (`BUFFER FULL`, блок не соблюдает STmin): целые записи из начала берём как есть, затем
   `19 02 01`, `19 02 08`, `19 02 04` — активные, подтверждённые, неподтверждённые отдельно (их мало, они влезают;
   неполной может остаться только история), блок помечен `truncated`.
4. `7F 19 11/12/7F` или молчание → KWP: для блоков за шлюзом BMW `18 02 FF FF` первым (серии E и MINI R5x понимают
   только группу FF FF, на FF 00 отвечают `7F 18 12` — лог MINI R56 17.10.2026), для остальных `18 02 FF 00`,
   `18 00 FF 00`, `18 02 FF FF` → `58 n [DTC2 + статус]×n`. **Тот же путь и за шлюзом**: до 17.10 там звался только
   разбор UDS, и 12 блоков MINI, ответивших `7F 19 11`, ушли в отчёт как «ошибок 0».
5. Иначе блок в списке с пометкой «отвечает, память ошибок не прочитана» и сырым ответом в журнале.

После UDS-ответа — `22 F190` (VIN) и `22 F187` (номер блока), как сейчас.
**Никогда**: `14`, `11`, `27`, `28`, `2E`, `31`, `3B`, `85`.

Формат кода: 2 байта SAE → `P0300`; третий байт ≠ 0 → `P0300-20`; формат блока «OEM» (BMW) → 6 hex по UDS,
4 hex по KWP (серии E: `A0B4`); байт статуса KWP марочный, в слова не переводится.
Сессия: если открывали `10 03`, после чтения ничего не делаем — она сама закроется через 5 с.

Следующая проверка: сначала опрос **только кеша** (10–15 с), полный перебор — если кеш пуст, старше 30 дней,
или пользователь нажал «Найти блоки заново» (экран данных). В отчёт идёт пометка «из кеша» / «полный поиск».

`ScriptedTransport` — реализация `ElmTransport` в тестах: таблица «команда → ответ» плюс состояние (текущий `ATSH`,
фильтр), которая отвечает как адаптер на машине. На нём гоняется весь `scanModules` целиком:
- машина «Hyundai 11 бит, пары +8»: 4 блока, у одного многокадровый ответ — находятся все, коды верные;
- машина «VAG MQB, пары +0x6A»: первый кадр без продолжений → ручной поток → полный ответ;
- машина «Honda 29 бит»: находится по `18DAF1xx`;
- машина «KWP-блок»: `7F 19 11` → `18 02 FF 00` → коды;
- «BMW через шлюз» на записи John (из `ParserTest`);
- урезанный клон (`ATCF` → `?`): путь 4.4 без падений;
- `7F 19 78` → повтор; `BUFFER FULL` → не падает, блок помечен.

CI: `gradle testDebugUnitTest` **перед** `assembleDebug`; красные тесты — красная сборка.
Все сырые обмены с живых машин (John и др.) складываются в `app/src/test/resources/traces/` и становятся тестами.

  не вышло — строка «двигатель не отвечает» (`klineEngineReconnectsAfterSweep`, `klineEngineLostIsReported`).

  значил бы «сохранён, сейчас не присутствует», но что BMW следует стандарту — не проверено, поэтому не переводим.
  Имена 0x00/0x02/0x30 на R56 по открытым источникам не подтверждены — ждём фото Launch с теми же кодами.

## 8а. Что изменилось после внешнего ревью (17.10.2026)

Отчёт сторонней модели (`docs/ПРОМПТ ДЛЯ ВНЕШНЕГО ИИ.md` → ответ в `docs/ТЗ/`) проверен по даташиту и открытому коду.
Взято:
- поиск без автопотока (`ATCFC0`) и зонд **`10 01 1`** — цифра ожидаемых кадров: ELM отдаёт «>» сразу после первого кадра;
  `10 01` раскрывает и KWP-блоки, которые на `19 02` молчат (`7F 10 12`);
- адрес, уже засветившийся как ID ответа, не зондируется как запрос;
- BMW: адреса 0x00–0xFF, верхняя половина только если нижняя не пуста;
- GM до Global B: `A9 81 12` при `ATCAF0`, ответ UUDT на `0x500 | (ответ & 0xFF)`, разбор `81 DTC FTB статус`;
- KWP по CAN: сессии `10 C0` / `10 92` / `10 89` перед `18 02 FF 00`;
- K-line Лада: ABS 20/28, подушки 27/58, ЭУР 30, электропакет 70, АПС A0, климат 36/29, приборка 60, парктроник 6A; `10 81`;
- подключение: ручной перебор 6→7→8→9→5 с `ATPC`, автопоиск ELM последним; `LV RESET` в лог.

Отвергнуто (противоречит даташиту): «при `ATCEA` ELM сам вставляет байт в данные FC» — пример даташита `ATFC SD 04 30 FF 00`
при `ATCEA 04` и EdiabasLib делают как у нас; `ATCER` — v2.2, на клонах нет; таблицы китайцев и Mercedes — непроверяемые,
имена по ним не ставим.

Ford MS-CAN / GM SW-CAN (только STN). Всё это — профили поверх каркаса из этого документа, не правки в нём.
